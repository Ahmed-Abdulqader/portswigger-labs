## 1. Objective
This lab contains a DOM-based cross-site scripting vulnerability in the search blog functionality. It uses an `innerHTML` assignment, which changes the HTML contents of a `div` element, using data from `location.search`. To solve this lab, perform a cross-site scripting attack that calls the `alert` function.

---

## 2. Background
This lab builds on the concepts from [Lab 3](03.%20DOM%20XSS%20in%20document.write%20sink%20using%20source%20location.search.md), but changes the sink from `document.write()` to `innerHTML`.
The `innerHTML` property is used to read or replace the HTML content inside an element. While it parses and renders most HTML tags (like `<img>`, `<svg>`, `<a>`, etc.), modern browsers deliberately **prevent `<script>` tags from executing** when they are inserted via `innerHTML`. This means that to exploit an `innerHTML` sink, you cannot use a standard `<script>` payload; you must use an HTML element combined with a JavaScript event handler (like `onerror` or `onload`).

## 5. Why It Worked
The payload worked because the application takes the `search` parameter from the URL (`location.search`) and assigns it directly to the `innerHTML` property of the `searchMessage` div without any sanitization.

This specific lab highlights a crucial quirk of `innerHTML`: **standard `<script>` tags do not execute when injected via `innerHTML`**. Browsers block script execution in this context for security reasons. 

To bypass this limitation, we must use an HTML element that triggers an event handler. By injecting `<img src=x onerror=alert(1)>`:
1. The browser parses the `<img>` tag as valid HTML.
2. It attempts to load the image from the invalid source `x`.
3. This causes an error, which immediately triggers the `onerror` event handler.
4. The JavaScript inside the event handler (`alert(1)`) executes successfully.

---

## 6. How to Fix It
To prevent this vulnerability, developers should avoid using `innerHTML` to insert user-controlled data. 

Instead, they should use `textContent` or `innerText`. These properties insert data as plain text rather than parsing it as HTML, which completely neutralizes the payload:

```javascript
// Vulnerable:
document.getElementById('searchMessage').innerHTML = query;

// Secure:
document.getElementById('searchMessage').textContent = query;
```

If HTML formatting is absolutely required, developers must use a safe HTML sanitization library (like DOMPurify) to strip out dangerous tags and attributes before assigning them to `innerHTML`.

*For more information, see: [OWASP DOM-based XSS Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html)*

---

## 7. Key Takeaway
When exploiting an `innerHTML` sink, standard `<script>` tags will not execute. You must use HTML elements with event handlers (like `<img onerror>` or `<svg onload>`) to trigger the JavaScript execution. To prevent this, developers should always use `textContent` instead of `innerHTML` for user input.
